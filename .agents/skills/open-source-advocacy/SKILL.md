# Open-source advocacy

Use this workflow only after the decision is merged or otherwise publicly
verifiable. Quality is more important than frequency.

1. Confirm that the subject is a meaningful engineering decision,
   contribution, or discovery with a concrete lesson. Skip routine updates,
   dependency churn, and posts whose only purpose is promotion.
2. Check `references/published-posts.md` and the live X profile for an existing
   post about the same decision. A draft, queue, or failed attempt is not a
   published post.
3. Research primary sources: the merged pH7Builder change, official project
   documentation, release metadata, licences, and contributor history. State
   trade-offs and version limits. Never infer a release from an unreleased
   branch.
4. Verify an X handle from the account itself or another authoritative source
   before tagging it. Omit the tag when identity is uncertain. Do not repeatedly
   tag maintainers for routine updates.
5. Review Pierre-Henry's recent technical posts and use his direct, personal,
   concise voice. Teach one useful decision. Prefer one post; use a short thread
   only when each post adds distinct value. Include the relevant public source
   link.
6. Remove hype, invented benchmarks, unsupported claims, confidential details,
   credentials, and private code. Never edit, propose, prefill, or save an
   account profile or bio description.
7. Publish through the connected Chrome session when authenticated access is
   available and the standing publication authorisation still applies. If it is
   unavailable, retain the prepared copy and report the blocker. Never claim a
   draft, preview, or queued item was published.
8. Open the live post from the public profile and verify its text, links,
   mentions, thread order, and public URL. Only then add one row to
   `references/published-posts.md` with the date, decision, source commit, and
   X URL.
